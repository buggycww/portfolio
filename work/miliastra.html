Miliastra Wonderland is a UGC mode inside Genshin Impact. I worked on a 3D Bomberman game within it as a game programming intern at Virtuos Kuala Lumpur, owning core gameplay logic from the bomb loop through the tutorial.

Professional Gameplay systems Grid Elemental interactions Onboarding

What I owned

  • Elemental bombs: placement, behaviour, and the interactions between bomb types.
  • Upgrade paths: progression that changes how the core bomb loop plays.
  • Grid system: clean placement and movement on a discrete board.
  • Range indicators: readable visual feedback for where a bomb will reach.
  • Skills and tutorial: the player’s abilities, plus the sequence that teaches the loop.

Integration is the job

The hardest part was not any single system. It was integration: reading an existing codebase, finding the right extension points, and deciding when a pragmatic version was enough versus when a reusable abstraction would pay for itself.

Early on I optimised for getting things working. That was useful for learning the codebase, but it created cleanup work when the feature grew. The lesson was not “always architect first.” It was: keep the integration boundary clean enough that you can refactor later without rewriting the feature.

The first version has to work. The second version has to fit.

What a playtest changes

A range indicator can look correct in the editor and still be unreadable in play. The project ran on daily stand-ups, regular playtests, and planning with designers and engineers, and that loop changed what I prioritised: clarity of the board state over additional simulation detail.

The same applied to the tutorial. It is not documentation bolted onto the game; it is the first level of the gameplay loop. Building it forced me to explain the bomb, the grid, and the upgrade path in the same language the player experiences them.

Constraints

What made it hard

A large existing codebase, an established feature set, and an NDA that rules out public screenshots. The work had to be understood through systems and decisions, not a trailer.

How I worked

Read the surrounding code before writing. Ask where the feature is supposed to live. Keep the first implementation small enough to test, then make the boundary explicit when the feature grows.

What I’d do differently

Spend more time reading patterns before the first commit. Write down integration assumptions so they can be challenged early. Instrument the grid and bomb state sooner, because a gameplay system you cannot observe is a gameplay system you cannot tune.

What I can share

No game assets or unreleased details — but I can talk through the systems, the integration decisions, the playtest loop, and what I would change. If you are hiring for a gameplay role, that conversation is the useful part.
